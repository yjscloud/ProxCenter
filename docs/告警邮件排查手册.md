# 告警邮件无法发送 —— 运维排查手册

> 适用对象：ProxCenter 值班 / 运维 / 二线支持
> 目标：**15 分钟内判定故障层级**，避免在 SMTP 上盲试
> 依据：本文所有路径与行号来自仓库当前代码；结论以代码行为为准，不以界面文案为准

---

## 0. 三条铁律（先记住，能省掉一半排查时间）

1. **`result=sent` 不代表邮件发出去了。**
   邮件 / 飞书 / 通用 Webhook 是三条独立通道，**任一成功即 `sent`**（`backend/app/alerting.py:1564-1576`）。
   飞书发成功会把邮件失败永久掩盖 —— 只看 `result` 必然误判。

2. **唯一可信的证据是告警历史里的 `detail` 原文。**
   格式固定为 `飞书：…；邮件：…；Webhook：…`（`alerting.py:1577`）。
   - `detail` 里**有**「邮件：<原因>」→ 真的尝试发过，按原因处理。
   - `detail` 里**没有**「邮件：」→ 这一轮按节奏/开关**根本没轮到邮件**，不是发送失败。

3. **资源告警的收件人跟「机器归属」走，不跟「规则配置者」走**（`alerting.py:2426-2428`、`:2497`）。
   管理员给全部虚机配规则，邮件会发给每台机器的主人；管理员自己一封都收不到是**设计行为**。

---

## 1. 链路全景（六层，按此顺序排除）

```
L0 调度层   后台作业「资源告警巡检」是否在跑、有没有报错、是否被 skip
      ↓
L1 触发层   规则启用？目标命中？PVE 连得上？（两处静默 return）
      ↓
L2 收件人层 这条告警落到谁头上？他有收件地址吗？（归属映射）
      ↓
L3 节流层   这一轮该不该发？（interval / max_repeats 独立闸门）
      ↓
L4 通道层   全局 SMTP 是否可用？（配置 → 网络 → 认证 → TLS）
      ↓
L5 投递后   对方收到了吗？（垃圾箱 / 网关拦截 / 地址写错）
```

每一层都有一个「一句话判据」和一组命令，见第 3 节。

---

## 2. 10 分钟分诊决策树

```
用户说「收不到告警邮件」
│
├─ ① 设置 → 邮件通知 → 测试发送（收件人填【当事人】地址）能收到吗？
│   ├─ 能 → SMTP 全局正常，问题在 L1/L2/L3，跳到 3.3
│   └─ 不能 → 读报错原文，直接跳到 3.5 的对照表
│
├─ ② 告警页历史里有出问题那台机器的记录吗？（只显示最近 80 条，查不到用 SQL）
│   ├─ 没有 → L0/L1/L2：作业没跑 / 没触发 / 记在别人名下
│   └─ 有 → 看 detail
│           ├─ 无「邮件：」段 → L3 节流
│           ├─ 「邮件：未配置收件地址」→ L2
│           └─ 「邮件：<网络或认证原因>」→ L4
│
└─ ③ detail 显示已发送，但用户说没收到 → L5（垃圾箱 / 网关 / 地址错）
```

**注意**：告警页历史只返回最近 80 条（`backend/app/routers/alerts.py:127`）。查不到不代表没发生，用第 4 节的 SQL。

## 3. 逐层检查清单

### 3.1 L0 调度层 —— 「巡检根本没在跑」

**判据**：作业状态页 `last_status`、`failures`、`skipped`、`last_error`。

- 「资源告警巡检」`enabled=false` → 永远不发（`app/scheduler.py:47-53`，配置持久化在 `settings.scheduler_jobs`）。
- 间隔被改成几小时 → 表现为「很久才有一封」。
- `last_status=error` + `last_error` → 作业本身抛异常（`scheduler.py:260-266` 会记 `类型: 消息`）。
- **`skipped` 持续增长是高频原因**：单封邮件超时 10 秒（`mailer.py:57`），一轮几十条告警时作业超过 60 秒，下一轮直接被跳过（`scheduler.py:299-304`）。现象是「告警邮件断断续续、隔几条丢一条」。

**命令**：

```bash
# 需要登录态；也可直接在「设置 → 后台作业」页面看
TOKEN='<你的 access token>'
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/api/scheduler \
  | python3 -m json.tool | grep -A12 '"id": "alerts"'

# 手动跑一轮资源告警巡检（等价于界面「立即执行」）
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8080/api/scheduler/alerts/run
```

### 3.2 L1 触发层 —— 「触发了，但静默中止」

代码里有两处**静默返回**，不写日志、不发通知，是「告警突然全没了」的经典原因：

| 位置 | 条件 | 表现 |
|---|---|---|
| `alerting.py:2453-2454` | PVE 连接未配置（`client.conn.configured` 为假） | 巡检每轮空转，什么都不做 |
| `alerting.py:2455-2458` | `cluster_resources()` 抛异常（PVE 掉线 / Token 失效） | 同上，且**不会**告警「PVE 连不上」 |

**判据**：仪表盘 / 虚拟机列表是不是也没数据？如果是，问题不在邮件，在 PVE 连通性。

**同时确认规则本身**：
- 规则是否 `enabled`；
- 目标是否被 `_match_target` 命中（节点名 / vmid 写错就永远不匹配）；
- 虚拟机磁盘类规则依赖 guest agent，取不到值会被记为「本轮不判定」（`alerting.py:2534-2538`），不是故障。

### 3.3 L2 收件人层 —— 「发给了别人」

**判据**：告警历史行的 `username` 就是**实际收件人**（不是配规则的人）。

- 虚机归 `alice`，规则由 `admin` 配 → 邮件发给 `alice`；
- 宿主机 / 无归属机器 → 回落到配规则的人（`RecipientBook`，`alerting.py:2481-2497`）；
- 端口 / SSH / 备份巡检同理：归「主机添加者」（`portguard.py:1467-1469`）。

**收件人为空**时 `detail` 是「未配置收件地址」（`alerting.py:1286-1287`）：用户既没填收件人，账号邮箱也是空的（`alerting.py:1267-1278`）。

**排查动作**：
1. 告警页确认「当前实际收件人：」那一栏显示的是谁；
2. 确认出问题机器归谁（虚拟机列表「归属」列 / 用户管理）；
3. 归属错了 → 后台「归属记录对账」作业会报无人认领的机器（`main.py:1457-1467`），可据此修正。

### 3.4 L3 节流层 —— 「这个点就是不该发」（最像故障的假故障）

邮件有**独立于飞书**的一套闸门（`alerting.py:2505-2570`）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `enabled` | `true` | 用户的告警邮件开关（`alerting.py:349-351`，默认开） |
| `interval` | `1800` 秒 | 同一告警两封之间最短间隔；**`0` = 只发首次** |
| `max_repeats` | `3` | 同一告警最多发几封（含首次）；`0` = 不限 |

判定逻辑：先看 `mail_count < max_repeats`，再看「首封 或 距上次 ≥ interval」。

**因此这些现象都不是故障**：
- 一台机器持续高负载，收到 3 封后就没动静了 → `max_repeats` 用满；
- 用户把 `interval` 设成 0 → 只有第一封；
- 告警恢复后 `alert_active` 行被清除，计数归零，下次告警会重新发。

**判据（SQL）**：

```sql
SELECT alarm_key, username, target, notify_source,
       FROM_UNIXTIME(NULLIF(mail_ts,0)) AS last_mail_at,
       mail_count
FROM alert_active
ORDER BY mail_ts DESC;
```

`mail_count` 已等于 `max_repeats` → 不是故障，调大上限或等恢复后重发。

> 另一个隐蔽点：**重复轮次没送达时，历史里连记录都不写**（`alerting.py:1934-1937`）。所以「历史空白」不能证明它没尝试过，只能结合 `mail_count` 判断。

### 3.5 L4 通道层 —— 真的去发了，被拒 / 超时

`send_mail` 会先做前置判断并直接返回中文原因（`mailer.py:361-372`）：

| detail 原文 | 层级 | 处理 |
|---|---|---|
| 邮件通知未启用 | 全局开关 | 设置 → 邮件通知 → 勾选「启用」并保存 |
| 未配置 SMTP 服务器 | 全局配置 | 填 host |
| 未配置发件人地址 | 全局配置 | 填 sender，或填 username 由它充当 |
| 没有收件人 | 收件人 | 见 L2 |

真正连服务器时的报错已被 `describe_error` 翻译（`mailer.py:270-349`），直接照做：

| detail 关键词 | 真实原因 | 处置 |
|---|---|---|
| 「TCP 能建立，但服务器 10 秒内没有返回问候语」 | **端口与加密方式不匹配**（最典型：465 配了 STARTTLS） | 465→SSL、587→STARTTLS、25→不加密（`mailer.py:257`） |
| 同上且端口没错 | 出站被防火墙 / 云厂商拦（阿里云、腾讯云默认封 25；部分邮箱停 587） | 换 465+SSL；放行出站 |
| 拒绝登录（535） | 用登录密码而非**客户端授权码**；或没开 SMTP 服务 | 生成授权码重填 |
| 被服务器拒绝（553 / 501） | 发件人与认证账号不是同一邮箱 | 统一 `sender` 与 `username` |
| TLS 握手失败 | 自签证书 | 关掉「校验服务器 SSL 证书」 |
| 无法解析服务器地址 | DNS / 内网域名 | 从**面板主机**上 `dig` 验证 |
| 拒绝连接 | 端口错或服务未监听 | `nc` / `openssl s_client` 验证 |

**只在升级 / 迁移后出现的特例**：SMTP 密码用 `SECRET_KEY` 加密存库（`mailer.py:124-133`）。换过密钥后解密失败会被**静默按「没配密码」处理**，只在日志留一行 warning，最终表现为 535。处置：管理员把密码重填一次并保存。

**连通性命令**（在**面板所在主机 / 容器内**执行，不要在自己电脑上测）：

```bash
# 1) 解析
getent hosts smtp.example.com || dig +short smtp.example.com

# 2) TCP 可达（465 走 SSL、587 走 STARTTLS）
nc -vz -w 5 smtp.example.com 465
nc -vz -w 5 smtp.example.com 587

# 3) 看服务器到底说不说话（这一步能区分「连不上」和「连上了不吭声」）
openssl s_client -connect smtp.example.com:465 -servername smtp.example.com </dev/null 2>&1 | head -5
openssl s_client -starttls smtp -connect smtp.example.com:587 </dev/null 2>&1 | head -5

# 4) Docker 部署要在容器内测（容器的出网策略可能和宿主不同）
docker exec -it <容器名> nc -vz -w 5 smtp.example.com 465
```

### 3.6 L5 投递后 —— 发出去了但没看到

面板侧看不出问题（SMTP 已返回 250），只能让对方查：

1. 垃圾邮件 / 广告邮件文件夹；
2. 企业邮箱的**隔离区 / 邮件网关拦截记录**（按发件人地址搜）；
3. 收件地址是否拼错、是否被填成群组地址被拆分丢弃；
4. 自建 SMTP 缺少 SPF/DKIM → 大概率被判垃圾邮件（建议改用服务商中继或补 DNS 记录）。

## 4. 命令速查

### 4.1 数据库连接

```bash
cd /data/proxcenter/backend
set -a; . ./.env; set +a          # 读取 DB_HOST / DB_USER / DB_PASSWORD / DB_NAME
mysql -h"$DB_HOST" -P"$DB_PORT" -u"$DB_USER" -p"$DB_PASSWORD" "$DB_NAME"
```

> 口令含特殊字符时改用 `mysql --defaults-extra-file=/root/.my.cnf`。

### 4.2 关键表与键

| 对象 | 位置 | 说明 |
|---|---|---|
| 全局 SMTP 配置 | `settings` 表，`key='mail_settings'` | 密码是密文，**不要**尝试还原 |
| 用户告警邮件配置 | `settings` 表，`key='alert_email:<用户名>'` | 收件人、开关、interval、max_repeats |
| 来源停推开关 | `settings` 表，`key='alert_notify_sources'` | 全局，管理员操作；关掉后**整条丢弃、不写历史** |
| 投递结果 | `alert_history` | `result` + `detail` 是唯一真相；`ts` 为秒级时间戳 |
| 当前告警与邮件计数 | `alert_active` | `mail_ts` / `mail_count` |
| 调度配置 | `settings` 表，`key='scheduler_jobs'` | 只存偏离默认值的作业 |

### 4.3 SQL

```sql
-- ① 全局 SMTP 配置（不含密码明文，只看 host/port/tls/enabled/verify_ssl）
SELECT `key`, LEFT(value, 500) AS cfg FROM settings WHERE `key`='mail_settings'\G

-- ② 某用户的告警邮件配置
SELECT value FROM settings WHERE `key`='alert_email:alice'\G

-- ③ 哪些来源被停推了（全局）
SELECT value FROM settings WHERE `key`='alert_notify_sources'\G

-- ④ 最近 20 条告警的投递明细（重点看 detail）
SELECT id, FROM_UNIXTIME(ts) AS t, username, target, kind, result, detail
FROM alert_history ORDER BY id DESC LIMIT 20\G

-- ⑤ 只挑涉及邮件的记录（中英文界面都要试）
SELECT id, FROM_UNIXTIME(ts) AS t, username, target, detail
FROM alert_history
WHERE detail LIKE '%邮件%' OR detail LIKE '%Email%'
ORDER BY id DESC LIMIT 30\G

-- ⑥ 某台机器 / 某个用户的近期告警
SELECT id, FROM_UNIXTIME(ts) AS t, target, result, detail
FROM alert_history
WHERE username='alice' AND target LIKE '%web-1%'
ORDER BY id DESC LIMIT 20\G

-- ⑦ 当前正在告警的对象与邮件发送进度
SELECT alarm_key, username, target, notify_source,
       FROM_UNIXTIME(NULLIF(mail_ts,0)) AS last_mail_at, mail_count
FROM alert_active ORDER BY mail_ts DESC;

-- ⑧ 近 24 小时各结果的条数（判断是否「一条都没发」）
SELECT result, COUNT(*) AS n FROM alert_history
WHERE ts >= UNIX_TIMESTAMP(NOW()) - 86400
GROUP BY result;
```

### 4.4 日志

日志格式：`%(asctime)s %(levelname)-8s %(name)s: %(message)s`（`backend/app/main.py:134-137`），
文件位置 `${ROOT}/logs/panel.log`（按天轮转，历史为 `panel.log-YYYYMMDD.gz`）；部分系统配置为标准输出，改看 journal。

```bash
# 实时跟踪（裸机部署）
tail -f /data/proxcenter/logs/panel.log | grep -E "邮件|mail|后台作业"

# 今天的发送失败与作业异常
grep -E "邮件发送失败|后台作业执行失败|邮件密码解密失败" /data/proxcenter/logs/panel.log

# 历史日期（轮转文件是 gz）
zgrep -hE "邮件发送失败|后台作业执行失败" /data/proxcenter/logs/panel.log-*.gz | tail -50

# systemd / journal 部署
sudo journalctl -u proxcenter --since "24 hours ago" \
  | grep -E "邮件发送失败|后台作业执行失败|邮件密码解密失败"

# 服务状态与最近重启时间（排除「进程一直没起来」）
systemctl status proxcenter --no-pager
```

**要记住的日志只有三句**：
- `邮件发送失败：<原始异常>`（`mailer.py:382`，WARNING，异常原文，中文解释在 detail 里）
- `后台作业执行失败：<作业名>（<id>）`（`scheduler.py:266`）
- `邮件密码解密失败，已按未配置处理`（`mailer.py:131`）← 换过 `SECRET_KEY` 的铁证

### 4.5 可绕开告警链路的独立验证

| 手段 | 路径 | 能证明什么 | 注意 |
|---|---|---|---|
| 设置页「发送测试」 | `POST /api/config/mail/test`（`routers/config.py:1268`） | SMTP 全局是否可用。**收件人填当事人地址** | 需 `settings.manage` |
| 密码重置邮件 | 登录页「忘记密码」 | 面板 → 用户邮箱整链路 | 完全绕开告警配置，最能区分「SMTP 坏」和「告警配置坏」 |
| 管理员下发 / 重装机器通知 | 机器操作面板 | 同上 | — |
| 告警页「模板测试」 | `POST /api/alerts/template/test` | **只能证明模板渲染** | ⚠️ 它刻意不看通道开关（`alerting.py:1587-1589`），成功**不能**作为「告警能发」的验收 |
| 告警页「立即检测」 | `POST /api/alerts/check` | 立刻触发一轮评估 | 管理员评估全部规则 |

## 5. 常见根因（按现场概率排序）

| # | 根因 | 一句话识别 | 处置 |
|---|---|---|---|
| 1 | 端口与加密方式不匹配（465 配 STARTTLS） | detail：「TCP 能建立但 10 秒没返回问候语」 | 465→SSL / 587→STARTTLS / 25→不加密 |
| 2 | 用了登录密码而非授权码 | detail：`拒绝登录（535 …）` | 换客户端授权码，先开 SMTP 服务 |
| 3 | 云主机出站 25/587 被封 | detail：超时或 refused，本机 `nc` 也不通 | 改 465+SSL；或放行出站 / 走中继 |
| 4 | 收件人跟归属走，发给了别人 | 历史行 `username` 不是反馈人 | 修正归属，或让本人确认 |
| 5 | `max_repeats` 用满（默认 3） | `alert_active.mail_count = 3` | 调大上限；恢复后自动归零 |
| 6 | 用户没填收件人且账号邮箱为空 | detail：「未配置收件地址」 | 补邮箱或填收件人 |
| 7 | 飞书成功掩盖邮件失败 | `result=sent` 但 detail 里「邮件：失败」 | 按 detail 处理；建议后续按通道分别记录 |
| 8 | 全局开关被关 / host 被清空 | detail：「邮件通知未启用 / 未配置 SMTP 服务器」 | 重新保存配置 |
| 9 | 换过 `SECRET_KEY`，密码解密失败 | 日志有「邮件密码解密失败」 | 重填密码保存 |
| 10 | 进垃圾箱 / 网关拦截 | 面板侧一切正常，对方收不到 | 查隔离区；补 SPF/DKIM |
| 11 | 巡检作业被 skip（SMTP 慢 → 超 60 s） | 状态页 `skipped` 增长 | 修 SMTP 延迟；或调大作业间隔 |
| 12 | PVE 掉线导致评估静默 return | 仪表盘同时无数据 | 先修 PVE 连接 |

## 6. 证据收集模板（复制到工单）

```markdown
### 告警邮件问题 · 现场证据

**基本信息**
- 面板版本 / 部署方式：        （systemd / docker，主机名）
- 反馈人（用户名）：            
- 首次发生时间 / 是否复发：      
- 期间是否升级过面板 / 改过 SMTP / 换过 SECRET_KEY： 

**范围**
- [ ] 所有邮件都收不到    [ ] 只有告警邮件    [ ] 只有个别人收不到
```

## 9. 一页速记

> 先看 `detail`，再看 `mail_count`，再看 `nc`。
> `result=sent` 不算数，`detail` 里没有「邮件：」就是不归邮件管。
> 收件人跟机器归属走，不跟配规则的人走。
> 465 配 SSL、587 配 STARTTLS，配错的表现是「连得上但不说话」。
