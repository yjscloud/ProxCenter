# 归属与安全数据边界

这份文档回答一个问题：**把一台资源指派（或收回）给另一个用户时，哪些数据跟着走、
哪些不跟、为什么**。改归属相关的代码散在 `app/ownership.py`、`app/hostscope.py`、
`app/alerting.py`、`app/routers/backups.py` 里，判断边界时以本文为准。

## 1. 一句话模型

> `resource_owner` 是 owner 的**唯一事实源**。所有可见性、额度、告警收件人都在
> **读取时**按它现算；业务行里另存的用户名（快照标记、备份 notes、规则条目）
> 只是历史 / 展示，不参与鉴权。

因此「指派」不是一个数据搬迁动作，而是**改一行 + 作废旧账**。凡是需要跟着走的
东西，靠「读时解析」自动跟随；凡是需要留下的东西（审计事实、主机级报告），
一律不搬。

## 2. 三个维度

| 维度 | 举例 | 归属键 | 改派语义 |
|---|---|---|---|
| 客户机 | 虚拟机、容器、快照 | `resource_owner`，`ref = <连接>:<节点>:<vmid>` | 改归属，快照标记清空（快照跟随机器） |
| 受管主机 | SSH 安全、登录审计、安全基线、端口与进程 | `resource_owner`，`kind = ssh_host`，`ref = host_id` | 改归属，四套安全数据**读取时**跟着变 |
| 面板账号 | 面板登录记录（`login_ips`）、操作审计 | `username` | **不可迁移**，那是「谁登录过」的事实 |

`host_id = "local"`（面板本机）固定只有管理员可见，**不可指派**。

## 3. 五类安全数据的边界

| 安全域 | 数据在哪 | 指派后 |
|---|---|---|
| 防火墙（guest 档） | PVE 原生；面板只有权限点与资源访问校验 | 权限随资源走，**不迁移规则** |
| 内网穿透规则 | 面板 `frp_rules`，按创建人归属；`guest_ref` 记目标机器 | 规则**不改归属**，但目标机器换主人后立即失效（不再渲染） |
| 防火墙（cluster / node 档）与规则模板 | PVE 原生 / 面板 `firewall_templates`（无 owner） | 与指派无关，**不授予也不收回** |
| SSH 安全 | 主机维度（受管主机） | 随**主机**改派跟随；guest 改派不触发 |
| 登录审计（面板） | `login_ips` / `audit_log`，账号级 | **永不迁移** |
| 登录审计（主机） | 按 `host_id`，主机维度 | 随主机改派跟随，历史记录 `username` 不改写 |
| 安全基线 | `inspection_host_report` / `inspection_history`，主键 `(namespace, host_id, lang)` | 随主机改派跟随（读时裁剪），**不搬报告** |
| 端口与进程 | 现场巡检 + 按 `host_id` 分键的人工处置 | 随主机改派跟随；处置状态不重置、不复制 |

关键约束：**guest 与 host 的归属互不推导**。一台受管主机可能承载多台 guest，
把某台 guest 交给新用户，绝不能连带把宿主机上的 SSH 爆破记录、端口清单交出去。

## 4. 改派时具体做了什么

统一入口（路由层不要自己 upsert）：

- `ownership.transfer_guest(kind, ref, username)` — 虚拟机 / 容器
- `ownership.transfer_host(host_id, username)` — 受管主机
- `ownership.forget_user(username)` — 删号

`transfer_guest` 依次做：

1. 读出改派前的归属（`previous`，写进审计，也是唯一能回答「原来是谁」的东西）；
2. 写 / 删 `resource_owner` 那一行（容器连带清 `KIND_VM` 下的历史幽灵行）；
3. 清这台机器名下的**快照归属标记**（含单连接时代的 `-:` 前缀）；
4. 把这台机器还挂着的**活动告警**改挂到新收件人名下；
5. 复核**内网穿透规则**：`guest_ref` 指向这台机器的规则，若作者已不是新主人，
   标记为失效（`stale`）并不再参与 frpc 渲染；有失效项时顺手重启 frpc 让隧道
   真正断开（见 `frp.annotate_rules` / `frp.restart_if_running`）；
6. 作废按人分档的读缓存：`dashboard:` / `snapshots:` / `backups:` / `search:` /
   `audit:actions:` + 额度读数；
7. 把 `settings.ownership_generation` 代际号 +1 —— `pvecache` 是进程内缓存，
   只清自己那份不够：多 worker 部署下别的进程仍会按旧账读到 TTL 到期。代际号
   一变，所有 worker 的旧条目一起作废（见 `pvecache.set_epoch_provider`）。

对应的路由：

| 接口 | 权限 | 审计动作 |
|---|---|---|
| `PUT /api/vms/{node}/{vmid}/owner` | `vm.assign` | `vm.assign` / `vm.unassign` |
| `PUT /api/lxc/{node}/{vmid}/owner` | `ct.assign` | `ct.assign` / `ct.unassign` |
| `PUT /api/ssh/hosts/{host_id}/owner` | `ssh.manage` | `ssh.host_owner` |

审计 `detail` 固定带 `previous`、`snapshots_removed`、`active_alerts_moved`、
`frp_rules_suspended`。

## 5. 删号时发生了什么

`DELETE /api/users/{username}` 依次：

1. `ownership.forget_user` — 清该账号**全部**归属行（所有 kind）。资源变无主，
   严格隔离下只有管理员可见，由管理员重新指派，不自动转给管理员；
2. `alerting.detach_owner` — 告警规则转为**无主**而不是删除：监控不能因为删号
   出现真空，无主规则在评估时归第一个管理员；
3. `frp.drop_rules_of` — 穿透规则**直接删除**：它是活的公网通道，账号没了没有
   保留的理由。注意已渲染的 frpc 配置要等下一次重载才少掉这条代理。

兜底：`quota.prune_deleted_owners`（周期作业 `owner_prune`）清掉归属表里指向
已不存在账号的记录；读不到账号表时整轮跳过。

## 6. 备份与备份计划

`[owner:x]` 写进 PVE 的 notes / comment，**只在机器已删除或无主时**作为回落依据。
生效归属一律是「归档 / 计划里 vmid 所属机器的**当前**归属」（见
`routers/backups.py:_effective_owner`）。这样机器改派后，备份下载 / 删除 / 计划
编辑的权限自动跟着机器走，而 PVE 侧那串标记不会被改派流程碰。

## 6.1 账号「不可用」时的告警投递

收件人按机器归属解析之后，还要回答「这个人现在收得到吗」。`RecipientBook` 的
判定是：账号存在 ∧ `enabled` ∧ 审批状态 `active` ∧ 未过期、未冻结。任一条不满足
就回落到规则创建人（管理员规则则是第一个管理员），并记一条日志说明原因。

**归属不改**：停用 / 到期是账号状态，不是资源处置；把机器自动划给别人是不可逆的，
而「告警没人收」是可以立刻修好的。这也是删号流程里对告警规则只做「转无主」而
不删除的同一条理由。

## 6.2 批量指派

`POST /api/vms/bulk` 增加 `assign` 动作（`routers/vms.py` → `app/bulk.py`），与单台
指派同一套语义：

- 权限按**目标类型**逐台判（`vm.assign` / `ct.assign`），并校验角色适用性；
- 逐台回报，一台失败不影响其余；失败的留在前端选择里可重试；
- **整批只做一次**全局收尾：`ownership.invalidate_caches()` + `frp.restart_if_running()`。
  逐台做的话，200 台就是 200 次缓存全量失效 + 200 个 1.5 秒的隧道空窗
  （`transfer_guest(notify=False, restart=False)`）；
- 不支持批量「清除归属」：一次抹掉 N 台机器的归属，误点代价太大，收回请单台操作。
  界面的提交按钮按「必须选人」禁用，服务端另有 `assign_target_error` 兜底（400）——
  脚本 / 第三方调用绕不过去。

## 6.3 指派理由 / 工单号

三个指派接口（VM / CT / 受管主机）都接受可选的 `reason`，只写进审计。改派是覆盖式
写入：`previous` 能回答「从谁到谁」，但「为什么改」只有这个字段能答。

批量指派走同一个字段（`POST /api/vms/bulk` 的 `params.reason`），逐台写进各自那条
审计 —— 一批 30 台只填一次理由，事后仍能按工单号把 30 条记录串起来。

## 6.4 备份归属对账（只读）

`GET /api/backups/owner-drift`（`settings.manage`）对照归档 notes 里的 `[owner:x]`
与机器**当前**归属，返回三类差异：

| reason | 含义 |
|---|---|
| `reassigned` | 标记写 A，机器现在归 B |
| `machine-unowned` | 机器已无归属（删了 / 收回了），标记还挂着 A |
| `unmarked` | 机器有归属，归档却没有标记（旧版本创建的） |

**只列不改**：不写 notes、不改归属。存量 notes 是历史事实，自动改写会把唯一还能
回答「这台机器以前归谁」的线索覆盖掉。界面入口在备份页标题栏（仅管理员）。

## 7. 已知缺口（明确未做，避免误以为已覆盖）

1. **存量穿透规则没有关联**：`guest_ref` 是后加的字段，升级前的规则读出来是空串
   （「未关联」），因此不会被改派复核。补齐有两个办法：管理员点规则卡片上的
   「重新关联目标机器」（`POST /api/frp/rules/relink`，只补空字段、按用户分组解析、
   解析不到的逐条返回），或让用户把规则重新保存一次。**不做自动回填**：反查依赖
   PVE 侧地址，PVE 不通时批量写入会把一批规则误判成「关联到别处」，而这个错误会
   直接决定一条隧道该不该断。
2. **巡检时间窗**：基线 / 端口巡检是长任务，改派不会等待也不会拒绝。当前判定是
   **不需要阻塞**：报告以 `(namespace, host_id)` 为键，属主机维度，不存在「半份
   报告跨归属分裂」；受影响的只是审计里「扫描开始时的主人」这一语境。
3. **只支持单 owner**：`resource_owner` 主键 `(kind, ref)`，没有「运维代管 +
   业务归属」的双角色模型。
4. **告警历史不迁移**：`alert_history.username` 是当时收件人的快照，改派后新主人
   看不到前任那段时间的告警记录（审计事实，刻意不改写）。

## 8. 新增改归属入口时的检查清单

- [ ] 是否走 `ownership.transfer_*` / `forget_user`，而不是直接 upsert？
- [ ] 审计是否记录了 `previous`？
- [ ] 是否引入了新的 owner 副本？如果引入了，它只能作展示 / 回落，且必须在
      注释里写清「不参与鉴权」。
- [ ] 读取侧遇到「归属指向不存在的账号」时，是否收敛到**不可见**而不是「不限」？
- [ ] 是否有按用户分档的新缓存？有的话补进 `ownership.CACHE_PREFIXES`。
- [ ] 是否引入了「用户自带的一条通道 / 凭据指向某台机器」？有的话在规则上记
      `guest_ref` 之类的关联，并在读取时按当前归属复核（参考 `frp.annotate_rules`）。
